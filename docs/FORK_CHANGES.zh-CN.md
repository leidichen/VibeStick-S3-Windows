## 1. 按键操作

StickS3 有三个键:**正面蓝色键**、**右侧键**、以及机身**左侧的电源键**(竖屏、屏幕朝向自己时)。

| 按键 | 手势 | 功能 |
|---|---|---|
| 蓝色键 | **长按**(300 ms 后触发) | 先响一声轻柔的双音提示,按住期间录音,松开后识别并粘贴 |
| 蓝色键 | 单击 | 在电脑上按**回车**(发送刚粘贴的内容) |
| 蓝色键 | 双击 | 立即刷新额度(平时每 5 分钟刷新一次) |
| 蓝色键 | 屏幕**熄灭**时的任何手势 | 只点亮屏幕,手势本身被吞掉,不会误触发 |
| 右侧键 | **单击** | **亮屏 / 息屏**(电脑搜索页打开时,单击 = *选下一台电脑*) |
| 右侧键 | **双击** | **切换 provider**(Codex ⇄ Claude) |
| 右侧键 | **连按三下** | **竖屏 ⇄ 横屏**(掉电后仍记住) |
| 右侧键 | 长按(450 ms) | 搜索局域网里的 bridge(电脑选择页) |
| 左侧电源键 | 单击 | 在我们这台设备上表现为重启(由电源管理芯片处理,不是本固件的功能) |
| 左侧电源键 | 长按 | 进入下载模式用于刷机(直到蓝灯双闪),见刷机指南 |

说明

- 右侧键要区分"单击 / 双击 / 三连击",所以单击的响应会有一个很短的延迟(不到一秒)。一个键放三种手势,这是代价。
- 正在录音时,右侧键不会把屏幕关掉。
- 电脑选择页里:右侧键 = 下一台,蓝色键 = 选定(与上游一致)。
- 上游用右侧键**单击**切换 provider;现在改成了**双击**。

## 2. 屏幕

**屏幕不会自己熄灭。** 上游在 5 秒无操作后关闭背光,这让设备没法当桌面显示器用。现在屏幕会一直亮着,直到你按一下右侧键。
有提醒到来(任务完成 / 出错 / 等待确认)时,它会自己亮起来;按任意键也会亮。

代价:亮屏费电。电池只有 250 mAh,要么一直接着 USB 供电,要么带着走的时候把屏幕关掉(见[电池](#3-电池))。

### 横屏

右侧键连按三下,在竖屏(135×240)和横屏(240×135,蓝色键在右边)之间切换,选择保存在闪存里(`nvs`,键名 `orient`)。

横屏布局:

```
[图标] Claude                  ● 运行中
5H  ━━━━━━━━━━━━━━━━━━━━━━━   87%
7D  ━━━━━━━━━━━━━━━━━━━━━━━   93%
WiFi         Upd 3m ago           🔋 65%
```

录音提示层和电脑选择页也有横屏版。横屏下,额度区的圆角边框和分隔线换成了两条通栏进度条。

### "多久前更新"

屏幕底部那行原来显示电脑名。现在只要 bridge 给了额度数据,它就显示**这些数字有多旧**:

| 数据年龄 | 文字 | 颜色 |
|---|---|---|
| 不到 1 分钟 | `Upd <1m ago` | 白 |
| 1~59 分钟 | `Upd 5m ago` | 10 分钟内白色,之后**黄色** |
| 1 小时 ~ 2 天 | `Upd 15h ago` | **红色** |
| 超过 2 天 | `Upd 3d ago` | 红色 |

年龄由**设备自己的时钟**从 bridge 给出的值开始往上数,所以即使 bridge 或电脑消失了,它也会继续变大。bridge 正常时会在
`<1m` 到 `5m` 之间循环(bridge 每 5 分钟刷新一次)。黄色表示刷新没有成功;红色通常表示 Claude 登录过期了
(见[第 6 节](#6-claude-额度数据新旧与登录自动续期))。没有年龄数据时(Codex,或还没取到过数据)这一行退回显示电脑名。

## 3. 电池

### 硬件事实

- StickS3 的电池只有 **250 mAh**,大约是手机电池的 5%。
- Espressif / M5 给出的耗电(4.2 V):关机 14 µA、ESP32 休眠约 102 µA、正常工作(开 Wi-Fi)约 37 mA、满载约 519 mA。
- 这个固件为了随时响应按键和显示提醒,**一直连着 Wi-Fi**。在我们这台设备上,满电、**熄屏**、保持 Wi-Fi 连接,大约撑了
  **15 小时**(平均约 17 mA,是估算值,因为电脑睡眠时日志有一段空白)。这和电池容量吻合,**没有发现电池损坏的迹象**。
- 实用建议:当桌面设备用时,**一直插着电**。以这个固件来说,它不是口袋设备。
- 有些商店把官方 *Hat 18650C* 电池底座标为兼容 StickS3,但 M5Stack 自己的 StickS3 页面明确写着它**结构上不兼容**。
  想延长续航,现实的办法是 USB-C 口接充电宝。
- USB 输入稳定在约 5.1~5.2 V 的充电头能正常给电池充电;而电脑上一个会掉到约 4.65 V 的 USB 口,充电标志几乎一直是 0。
  这个对比我们只有几分钟的数据,只能当线索,不是结论。

### 电量百分比为什么不准,现在怎么算

设备没有电量计,百分比是靠电池电压估的。上游每次读数都用 `(mV − 3300) / 800`。在我们设备上充电时实测:

- 端电压会随充电器的行为**抖动 30~55 mV**(有电流时升高,暂停时回落)。旧公式把每次抖动放大成 4~7 个百分点,
  比如一分钟前 67%、一分钟后 60%。
- 它要 ≥ 4100 mV 才显示 100%,但这块电池加这个充电器实际停在 **4.06~4.09 V**,所以**永远到不了 100%**。
- 充满的平台期里,显示的数字在 2.5 小时里变了 **577 次**。

`firmware/sticks3/src/vibe_battery.c` 现在这样处理:

1. **取最近 5 次读数的中位数**(每 15 秒读一次)——滤掉负载冲击和充电纹波。
2. **"充电器说满了"锁存**:插着 USB、电压 ≥ 4040 mV,且最近 6 分钟里充电标志至少翻转 4 次(充电器在反复补电)→ 显示
   **100%**,直到拔掉线或电压跌破 4000 mV。
3. **滞回**:插着 USB 时,变化不到 2 个点就不动;用电池时数值只会**下降**,除非一次明显回升 ≥ 10 个点(比如静置很久之后)。
4. 插拔 USB 之后,显示先保持 2 次采样不动,因为那一刻电压会台阶式变化几十毫伏。
5. 重启后需要约 3 分钟的历史,才能判定"已充满"。

把我们自己 1058 条充电日志用同一份 C 代码回放:显示变化次数 787 → 25,平台期变化 577 → 2,锁存在 4052 mV 时触发
(平台实际从 11:53 开始,锁存在 11:56)。这个回放不需要硬件,见下文。

所以"100%"的意思是 *充电器认为电池已充满*,和手机一样,不代表电芯还保有出厂标称容量。阈值(4040 / 4000 mV、翻转 4 次)是在
**一块**电池上调的,换电池可能需要重新校准。

### 遥测与工具

设备每 15 秒记录一条原始读数,批量通过 Wi-Fi 上传给 bridge(`POST /battery`,需要 bridge token)。bridge 连不上时,样本先放在设备里
一个 160 条的环形缓冲区(约 40 分钟),恢复后补传;每条样本带着自己的"几秒前",所以设备不需要实时时钟。

bridge 把它们追加到 `battery_log.csv`(在 bridge 的应用数据目录里;可用 `VIBE_STICK_BATTERY_LOG` 改位置;超过 10 MB 自动轮转)。

| 列 | 含义 |
|---|---|
| `bat_mv` | 电池端电压原始值 |
| `vin_mv` | USB 输入电压(插着约 4600~5400,没插为 0) |
| `charging`、`usb` | 充电标志、USB 是否供电 |
| `pct_shown` | 屏幕上当时显示的百分比 |
| `screen_on`、`recording` | 当时是否亮屏 / 是否在录音 |
| `audio_idle_s` | 距离上次扬声器或麦克风工作过多少秒(用来识别"发声造成的电压下陷") |

- `python bridge/tools/battery_report.py [--hours 12]`:按供电状态分段,给出电压斜率,列出电压突变及可能原因,并给出启发式判断。
  结论只是提示,**不是电池健康检测**;真正的容量测试需要一次受控的完整放电。
- `firmware/sticks3/tools/host_battery_test.c`:在电脑上编译同一份 `vibe_battery.c`,跑 6 个合成场景,也能回放 CSV:
  `cl /I..\include host_battery_test.c ..\src\vibe_battery.c`(或用 `cc`),然后 `host_battery_test.exe battery_log.csv`。

## 4. 声音

| 声音 | 何时 | 内容 |
|---|---|---|
| **准备提示**(新增) | 长按蓝色键,**麦克风打开之前** | 静音 100 ms、880 Hz 70 ms、间隔、1320 Hz 100 ms |
| 完成 | 任务完成 | 内置双音蜂鸣(880 / 1320 Hz)。**可选自定义音频**,见下 |
| 出错 / 识别失败 | | 240 Hz ×3(上游) |
| 等待确认 | | 600 → 800 Hz(上游) |

- 准备提示在麦克风启动**之前**播放,所以不会被录进去。响完后稍停半拍再开口:录音开头约 130 ms 本来也会被丢弃
  ([第 5 节](#5-语音输入))。
- 扬声器功放被打开后,前约 100 ms 的声音会被吞掉,所以提示前面加了静音(单独一个 45 ms 的"滴"完全听不见)。低音量的 1900 Hz
  也听不见;880 / 1320 Hz 很清楚。
- M5Stack 的 StickS3 页面建议用电池供电时扬声器音量不超过 75%,否则可能因为耗电过大而复位。

### 自定义"完成"音

这个 fork 的作者用了一段自定义音频。**仓库里不带任何音频文件**:它的来源和授权我们不清楚,安全的默认值是内置蜂鸣。想用自己的声音:

```
python firmware/sticks3/tools/make_done_sound.py my_sound.wav      # 16 位 PCM WAV,任意采样率 / 声道
```

它会生成 `firmware/sticks3/src/vibe_done_sound.h`(已被 git 忽略)——16 kHz 单声道、裁掉首尾静音、峰值归一化(最长 3 秒)。
编译时这个文件存在,固件就以 0.55 倍音量播放它(`vibe_audio.c` 里的 `VIBE_DONE_SOUND_GAIN`);不存在就回退到蜂鸣。请只使用你有权使用的音频。

## 5. 语音输入

一句话的时间线:

```
长按 ─300 ms─▶ 准备提示 ─▶ 麦克风打开(约 55 ms)─▶ 你说话 ─▶ 松开
   ─▶ S3 上传 PCM ─▶ bridge:[裁掉开头 130 ms] ─▶ 识别 ─▶ 粘贴到当前窗口
```

- **长按判定 450 → 300 ms,并加了准备提示**:上游要按满 450 ms 才开麦,一按下去就说话的人会丢掉开头一两个字。
  现在提示音响完就能确定已经在录。我们的设备上,麦克风在提示音结束后约 55 ms 打开。
- **裁掉开头 130 ms**(`VIBE_STICK_TRIM_START_MS`)。编解码器的 ADC 上电时会产生一个直流台阶,在配置的 36 dB 输入增益下削顶到满量程,
  再在约 130 ms 内衰减(51 条录音每一条开头都有,包括提示音出现之前录的,所以不是提示音漏进去)。这段里没有语音。
- **提前识别**(`VIBE_STICK_PREFETCH_ASR`,默认开):音频文件一到就开始识别,与设备的"停止"请求并行,而不是等它之后。
- **本地离线识别**(可选):通过 [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) 运行 SenseVoice。设置
  `VIBE_STICK_LOCAL_ASR=sensevoice`,并让 `VIBE_STICK_LOCAL_ASR_MODEL_DIR` 指向含 `model.int8.onnx` 和 `tokens.txt` 的文件夹。
  依赖用 `pip install "./bridge[local-asr]"` 安装。任何本地失败(缺包、缺模型、解码出错)都会**回退到已配置的云端识别**,所以模型坏了
  也不会让语音输入哑掉。本地路径正常时,没有音频离开你的电脑。我们不分发模型,请从 sherpa-onnx 的发布页下载
  (`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17.tar.bz2`,约 1 GB,只需要其中约 230 MB 的 int8 模型和 `tokens.txt`),并自行确认其许可证。
  bridge 启动时加载模型需要 2~5 秒,约占 340 MB 内存。
- bridge 日志里每次录音会有一行 `timing …`(上传、保存、识别、粘贴各段耗时)。

在真机 + 真 bridge 上的实测(日志里的 `timing` 行)。"音频到达 → 粘贴完成"从 bridge 收到上传请求的那一刻算起,所以包含通过
Wi-Fi 接收 PCM 的时间:

| | 改前 | 改后 |
|---|---|---|
| 识别 | 云端 0.5~1 秒,有一次冷请求 8.9 秒 | 本地 0.15~0.75 秒(5 秒录音约 0.35 秒),稳定 |
| bridge 对音频上传和停止请求的应答 | 各 1.4~2.7 秒(每次请求起两个 PowerShell) | 约 0.04 秒([第 7 节](#7-bridge-的修复与性能)) |
| 整个粘贴步骤 | 约 350 ms | 约 106 ms(写剪贴板约 310 ms → 约 1 ms;其余是按下 Ctrl+V 之后故意等的 100 ms) |
| 音频到达 → 粘贴完成 | 5 秒录音约 3.0 秒(云端) | 0.55 秒(2.8 秒录音)、1.1 秒(6~8 秒)、1.9 秒(11 秒)、2.4 秒(20 秒) |

云端识别仍作为回退保留。我们的五句测试里,本地和云端文字除了一两个字之外一致(两边都是 SenseVoice),没有看到质量下降;
但五句话不是基准测试。

## 6. Claude 额度:数据新旧与登录自动续期

Claude 的 5H / 7D 数字来自 Anthropic 一个**未公开**的接口,用的是 Claude Code 保存在 `~/.claude/.credentials.json` 里的
OAuth 令牌。我们实测到两件事:

- 这个访问令牌**大约 8 小时**有效,而且**只有 Claude Code 命令行版**会续期。桌面 App 用自己的登录,从不更新这个文件。
  所以 8 小时后数字就悄悄变旧了。
- Anthropic 随时可能修改或下线这个接口。

这个 fork 的做法:

1. **显示数据的新旧**([第 2 节](#多久前更新)),让过期的数字一眼就能看出来,而不是看着像真的。
2. **自动续期登录**。当保存的令牌已过期,bridge 会在后台、至多每 20 分钟一次,执行:

   ```
   claude -p "reply with: ok" --model haiku --no-session-persistence --setting-sources project --tools ""
   ```

   让命令行版去续*它自己的*凭据。bridge 自己从不读取或使用刷新令牌。这个调用跳过你的 hooks(`--setting-sources project`)、
   不留会话文件、并从环境里去掉 `CLAUDE_CODE_OAUTH_TOKEN`。代价:每次约 1 万个缓存 token,一天约 3 次。
   用 `VIBE_STICK_CLAUDE_TOKEN_REFRESH=off` 关闭;用 `VIBE_STICK_CLAUDE_CLI` 指定可执行文件。日志里找 `claude login refresh … ok|FAILED`。
3. 如果失败(刷新令牌也过期了——大约每 30 天一次——或没有网络),在终端运行一次 `claude`,然后 `/login`。

已经用假 CLI 做了单元测试,也用真实的 `claude -p …` 命令从 bridge 的 Python 里手动跑过一次(约 7 秒,退出码 0,没有写会话文件)。
**令牌真正过期时的自动触发还没有被观察到**——请在第一天留意日志里的 `claude login refresh`。

## 7. bridge 的修复与性能

- **"任务完成"提示音时有时无。** 原来的判断要求 `end_turn` 记录是**所有会话里**最新的一条。但 Claude Code 在有 Stop hook 时,会在一轮结束约
  2 秒*之后*再写一条 `system/stop_hook_summary`,另外其它打开的会话也在写记录,提醒经常被吞掉。现在忽略纯记账的 `system` 记录
  (但带错误 / 取消信号的 `system` 记录仍然算),并且"最新"按**每个会话各自**判断。回归测试覆盖了这两点和取消的情形。
- **空闲 CPU 与延迟。** 原来每个状态请求都会起两个 PowerShell 进程(每个 provider 一个),并重新解析最多 40 个、每个最多 1.5 MB 的会话文件。
  现在由一个共享的、后台每 10 秒刷新的进程快照代替 PowerShell 调用,解析过的会话文件按 `(修改时间, 大小)` 缓存。实测:空闲 bridge 的
  CPU 约 7% → 约 0.9%(单核),`GET /state` 约 270 ms → 约 36 ms,没变化时一次 Claude 观察约 287 ms → 约 10 ms。
- **粘贴**通过 Win32 接口写剪贴板(约 1 ms),不再起 PowerShell(约 310 ms);PowerShell 保留作回退。
- **额度年龄**:`/state` 里的 `provider.quota_age_s`;额度快照里保存了真实的取数时间戳。
- **电池遥测**接口(`POST /battery`,需要 token)。

## 8. 新增配置项

全部可选,见 `.env.example`。

| 变量 | 默认 | 含义 |
|---|---|---|
| `VIBE_STICK_LOCAL_ASR` | 关 | `sensevoice` 启用本地识别 |
| `VIBE_STICK_LOCAL_ASR_MODEL_DIR` | – | 含 `model.int8.onnx` 和 `tokens.txt` 的文件夹 |
| `VIBE_STICK_LOCAL_ASR_THREADS` | 8 | CPU 线程数(1~16) |
| `VIBE_STICK_PREFETCH_ASR` | 开 | 音频一到就开始识别 |
| `VIBE_STICK_TRIM_START_MS` | 130 | 每段设备录音开头裁掉多少毫秒;0 = 不裁 |
| `VIBE_STICK_CLAUDE_TOKEN_REFRESH` | 开 | Claude Code 登录过期时自动续期 |
| `VIBE_STICK_CLAUDE_CLI` | PATH 里的 `claude` | Claude Code 可执行文件路径 |
| `VIBE_STICK_BATTERY_LOG` | 应用数据目录 | 电池遥测 CSV 位置 |

配置读取顺序(与上游一致):bridge **先**读 `<应用数据目录>/VibeStick/.env`,再读 `./.env`;同一变量以先读到的为准。应用数据目录里
遗留的旧副本会覆盖你正在编辑的那份。

## 9. 编译、刷入、测试

- Windows 的分步指南:[WINDOWS_QUICKSTART.zh-CN.md](WINDOWS_QUICKSTART.zh-CN.md)。
- Wi-Fi 名称 / 密码、bridge 地址和 token 都是**编译进固件**的(`vibe_stick_secrets.h`),所以没法分享预编译好的固件——每个人都要自己编译。
  改其中任何一项都需要重新刷入。
- 刷机需要 USB-C **数据线**。没有无线升级(分区表是单应用)。
- 测试:`PYTHONPATH=bridge/src python -m unittest discover -s tests`(CI 跑的就是这个)。有两个测试要编译 C 代码,PATH 里没有
  `cc`/`gcc`/`clang` 时会被跳过。

## 10. 已知限制

- **电池很小**(见上)。连着 Wi-Fi 时,它是桌面伴侣。
- **设备只能在同一局域网里找到电脑。** 电脑 IP 变了,设备会一直离线,直到你再长按右侧键搜索(建议给电脑固定 IP / DHCP 保留)。
- **电脑睡眠 = 设备断连。** 此时设备会不停地重试 Wi-Fi / HTTP,可能更费电(没有实测)。
- **安全。** bridge token 以明文 HTTP 头传输,在你搜索电脑时还会通过 UDP 广播发出;拿到它的人能让你的电脑按回车或粘贴语音文字。
  `GET /state` 不需要 token,会暴露电脑名和额度;写入类接口需要 token。Wi-Fi 密码和 token 任何人把设备插上电脑就能读出来。
  只在可信的局域网里使用,并把防火墙规则限制在你的子网内。
- 电池阈值是在一块电池上调的。
- Claude 额度依赖一个未公开的接口,可能随时失效。
- Windows 上 bridge 的后台运行用的是上游的 `install_windows.ps1`(隐藏的计划任务)。在作者的电脑上这些任务无法启动(错误 `0x80070002`),
  后来改用了手写的托盘启动器;这是否影响别的电脑,不清楚。
